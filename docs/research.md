# Операционная система NixOS: настройка, эксплуатация и исследование воспроизводимости систем

## Аннотация

В данной работе рассматривается операционная система NixOS, основанная на декларативном подходе к управлению программным обеспечением и системной конфигурацией.

В отличие от традиционных дистрибутивов Linux, где настройка системы часто выполняется посредством последовательности команд, NixOS позволяет описывать желаемое состояние операционной системы в виде конфигурационных файлов на языке Nix.

Цель исследования — изучить механизмы воспроизводимости, особенности установки и эксплуатации NixOS, оценить преимущества и недостатки декларативного подхода, а также исследовать возможности автоматизированного создания системных образов и клонирования конфигураций по сети.

Особое внимание уделяется вопросу: **возможно ли получить две функционально эквивалентные операционные системы, используя один набор конфигурационных файлов, и какие условия необходимы для достижения такого результата?**

Для ответа предлагается провести сравнительный анализ подходов к администрированию Linux и разработать экспериментальный стенд на основе виртуальных машин.

**Ключевые слова:** NixOS, Linux, Nix, декларативная конфигурация, воспроизводимые сборки, автоматизация, системные образы, виртуализация, Git.

## 1. Введение

### 1.1. Актуальность темы

Современные информационные системы часто состоят из множества серверов, виртуальных машин и рабочих станций, которые необходимо устанавливать, обновлять и поддерживать.

В традиционных дистрибутивах Linux настройка обычно включает последовательное выполнение команд установки пакетов, редактирование конфигурационных файлов и запуск необходимых служб.

Например, для настройки веб-сервера на Ubuntu могут использоваться команды:

```bash
sudo apt update
sudo apt install nginx
sudo systemctl enable nginx
sudo systemctl start nginx
```

После этого администратор может изменять дополнительные настройки, устанавливать другие программы и редактировать системные файлы.

Такой подход достаточно прост, однако со временем возникает ряд проблем:

1. Сложно восстановить точную последовательность выполненных изменений.
2. Две машины, настроенные похожим образом, могут иметь разные версии программ и зависимостей.
3. Обновление программного обеспечения иногда нарушает работоспособность существующей конфигурации.
4. Для восстановления сервера после сбоя может потребоваться повторное выполнение большого количества действий.
5. Фактическое состояние системы не всегда соответствует имеющейся документации.

Особенно заметными эти проблемы становятся при эксплуатации нескольких серверов.

Одним из способов решения является подход **Infrastructure as Code (IaC)** — «инфраструктура как код», при котором параметры инфраструктуры описываются в конфигурационных файлах и хранятся в системе управления версиями.

NixOS развивает эту идею на уровне самой операционной системы.

### 1.2. Цель исследования

Исследовать возможности NixOS для воспроизводимой установки, настройки и эксплуатации Linux-систем и определить ограничения декларативного управления.

### 1.3. Задачи исследования

Для достижения поставленной цели необходимо:

1. Изучить архитектуру NixOS и пакетного менеджера Nix.
2. Рассмотреть принципы воспроизводимых сборок.
3. Исследовать основные способы установки NixOS.
4. Проанализировать преимущества и недостатки декларативного подхода.
5. Изучить создание образов операционной системы по конфигурации.
6. Рассмотреть автоматизированное развёртывание систем через локальную сеть.
7. Разработать методику экспериментальной проверки воспроизводимости.
8. Сформулировать критерии оценки полученных результатов.

### 1.4. Гипотеза исследования

**Предполагается, что использование NixOS с зафиксированными зависимостями позволяет существенно упростить воспроизведение системной конфигурации на нескольких компьютерах по сравнению с ручным администрированием.**

При этом идентичность конфигураций не обязательно означает побитовую идентичность всех программных сборок и полное совпадение состояния работающих машин.

Эта гипотеза должна быть проверена на практическом стенде.

## 2. Архитектура и особенности NixOS

### 2.1. Что такое NixOS

NixOS — дистрибутив Linux, использующий функциональный пакетный менеджер Nix и декларативную систему конфигурации.

Для понимания его архитектуры необходимо различать три компонента:

| Компонент | Назначение |
|---|---|
| Nix | Пакетный менеджер и система сборки программ |
| Nixpkgs | Коллекция описаний программных пакетов и библиотек |
| NixOS | Операционная система, построенная с использованием Nix и модульной системы конфигурации |

Главная особенность NixOS состоит в том, что большая часть системных настроек задаётся не последовательностью команд, а описанием желаемого результата.

Например, вместо ручной установки и настройки веб-сервера можно записать:

```nix
{
  services.nginx.enable = true;
}
```

После применения конфигурации NixOS подготовит необходимые компоненты для работы Nginx.

Это описание можно хранить в Git, переносить между компьютерами и использовать повторно.

### 2.2. Каталог /nix/store

В обычных Linux-дистрибутивах программное обеспечение устанавливается преимущественно в общие системные каталоги, например:

- `/usr/bin`
- `/usr/lib`
- `/etc`

Nix использует специализированное хранилище:

```text
/nix/store/
```

Пример пути установленной программы:

```text
/nix/store/<hash>-nginx-<version>/
```

Здесь `<hash>` — часть имени пути в хранилище, формируемая Nix с учётом информации о сборке или содержимом в зависимости от типа объекта.

Это позволяет хранить разные версии одного программного пакета параллельно.

Например, две версии библиотеки могут существовать одновременно, не перезаписывая друг друга.

Важным свойством является то, что объекты хранилища Nix рассматриваются как неизменяемые после создания.

В результате обновление пакета обычно приводит к созданию новых объектов, а не к изменению существующих файлов на месте.

Однако наличие хеша в имени пути **не означает автоматически**, что программа была независимо собрана с побитово идентичным результатом.

### 2.3. Поколения конфигураций

NixOS поддерживает механизм поколений (*generations*).

При изменении системной конфигурации создаётся новое поколение системы. Старые поколения могут сохраняться, что позволяет возвращаться к предыдущему состоянию системного программного обеспечения.

Для применения изменений используется:

```bash
sudo nixos-rebuild switch
```

Для возврата к предыдущей системной конфигурации:

```bash
sudo nixos-rebuild switch --rollback
```

Существует также команда:

```bash
sudo nixos-rebuild test
```

Она активирует новую конфигурацию без назначения её конфигурацией по умолчанию для следующей загрузки.

Таким образом, обновления NixOS обладают механизмом отката, который полезен при экспериментировании с системными настройками.

Следует учитывать, что откат системной конфигурации не равнозначен восстановлению всех пользовательских данных и баз данных. Например, изменение содержимого базы данных не отменяется автоматически при возвращении к предыдущему поколению NixOS.

## 3. Воспроизводимые сборки

### 3.1. Определение воспроизводимой сборки

Согласно проекту [Reproducible Builds](https://reproducible-builds.org/), сборка считается воспроизводимой, если из одинакового исходного кода, при одинаковых существенных параметрах окружения и инструкциях сборки, независимые участники могут получить побитово идентичные артефакты.

Например, если два разработчика собирают одну программу из одного исходного кода, полученные исполняемые файлы должны иметь полностью одинаковое содержимое.

Это позволяет проверять, соответствует ли распространяемый программный пакет ожидаемому результату сборки.

Преимущества воспроизводимых сборок:

- повышение прозрачности процесса разработки;
- возможность независимой проверки программных артефактов;
- выявление неучтённых зависимостей и недетерминированного поведения;
- повышение доверия к поставляемому программному обеспечению;
- упрощение анализа различий между сборками.

### 3.2. Как Nix помогает воспроизводимости

В традиционных системах результат сборки может зависеть от установленной версии компилятора, системных библиотек и других внешних факторов.

Nix позволяет явно описывать зависимости и инструкции сборки.

Например:

```nix
{ pkgs ? import <nixpkgs> {} }:

pkgs.stdenv.mkDerivation {
  pname = "example";
  version = "1.0";

  src = ./src;

  nativeBuildInputs = [
    pkgs.gcc
  ];

  buildPhase = ''
    gcc main.c -o example
  '';

  installPhase = ''
    mkdir -p $out/bin
    cp example $out/bin/
  '';
}
```

В данном примере описывается сборка простой программы на языке C.

Система Nix использует декларативное описание для подготовки зависимостей и выполнения сборки.

Однако этот пример сам по себе ещё не гарантирует полной воспроизводимости: необходимо также контролировать версию Nixpkgs, содержимое исходного кода и возможные недетерминированные факторы.

### 3.3. Nix Flakes и фиксация зависимостей

Одним из инструментов управления зависимостями являются **Nix Flakes**.

Flake-проект использует файл:

```text
flake.nix
```

В нём описываются входные зависимости и результаты проекта.

Дополнительно создаётся:

```text
flake.lock
```

Этот файл фиксирует конкретные ревизии зависимостей.

Пример:

```nix
{
  description = "NixOS research project";

  inputs.nixpkgs.url =
    "github:NixOS/nixpkgs/nixos-26.05";

  outputs = { nixpkgs, ... }: {
    nixosConfigurations.lab =
      nixpkgs.lib.nixosSystem {
        system = "x86_64-linux";

        modules = [
          ./configuration.nix
        ];
      };
  };
}
```

Для создания или обновления файла фиксации зависимостей можно использовать:

```bash
nix flake lock
```

Файлы `flake.nix` и `flake.lock` следует сохранять в Git.

Благодаря этому возможно повторно использовать те же ревизии зависимостей.

При этом важно учитывать два ограничения.

Во-первых, Flakes в документации Nix по-прежнему описываются как экспериментальный формат с некоторыми нерешёнными особенностями.

Во-вторых, фиксация зависимостей не устраняет автоматически все причины недетерминированности при сборке программ.

### 3.4. Три уровня воспроизводимости

Для данного исследования предлагается разделять воспроизводимость на три уровня.

| Уровень | Что воспроизводится | Как проверять |
|---|---|---|
| Конфигурационный | Описание пакетов, служб и параметров системы | Сравнение конфигураций, lock-файлов и вычисленных результатов |
| Сборочный | Программные артефакты | Независимая повторная сборка и сравнение содержимого |
| Эксплуатационный | Работа служб и наблюдаемое поведение системы | Функциональные тесты на нескольких машинах |

Эти уровни связаны между собой, но не являются тождественными.

Например, две виртуальные машины могут быть установлены по одной конфигурации и успешно предоставлять одинаковый веб-сервис, но при этом иметь разные IP-адреса, SSH-ключи, журналы и идентификаторы системы.

Следовательно, их функциональная эквивалентность не означает полного совпадения содержимого дисков.

**Промежуточный вывод:** NixOS создаёт условия для воспроизводимого управления системой, но степень фактической воспроизводимости зависит от контролируемых входных данных, среды сборки и состояния системы во время эксплуатации.

## 4. Установка NixOS

### 4.1. Установка в качестве основной операционной системы

Первый способ предполагает установку NixOS непосредственно на физический компьютер или виртуальную машину.

Стандартная процедура включает следующие этапы:

1. Загрузка установочного ISO-образа с официального сайта.
2. Запуск компьютера с установочного носителя.
3. Разметка накопителя и создание файловых систем.
4. Монтирование подготовленных разделов.
5. Генерация конфигурации оборудования.
6. Настройка системы.
7. Установка NixOS.
8. Перезагрузка в установленную систему.

После подготовки и монтирования файловых систем используется команда:

```bash
sudo nixos-generate-config --root /mnt
```

Она создаёт начальные конфигурационные файлы, включая:

```text
/mnt/etc/nixos/configuration.nix
/mnt/etc/nixos/hardware-configuration.nix
```

Первый файл содержит настройки системы, а второй — информацию о конфигурации оборудования и файловых системах.

После их редактирования выполняется:

```bash
sudo nixos-install
```

При использовании Flakes команда установки должна дополнительно ссылаться на соответствующую flake-конфигурацию.

**Преимущество:** полный контроль над конфигурацией операционной системы.

**Недостаток:** первоначальная установка и настройка загрузчика, разделов и оборудования требуют понимания устройства Linux.

### 4.2. Использование Nix поверх другого Linux-дистрибутива

Пакетный менеджер Nix можно установить в существующую операционную систему, например Ubuntu, Debian или Fedora.

Официальная команда установки Nix с многопользовательским режимом:

```bash
curl --proto '=https' --tlsv1.2 \
  -L https://nixos.org/nix/install \
  | sh -s -- --daemon
```

Перед выполнением такого установщика следует ознакомиться с его документацией и требованиями безопасности.

После установки можно использовать Nix для управления программами и окружениями разработки.

Однако необходимо учитывать принципиальное различие:

**Установка Nix поверх Ubuntu не превращает Ubuntu в NixOS.**

В таком случае ядро, системные службы и базовая инфраструктура продолжают управляться исходным дистрибутивом.

Этот вариант подходит для изучения Nix без переустановки существующей операционной системы.

### 4.3. Замена существующей системы на NixOS

NixOS также можно развернуть на компьютере, где уже работает другой Linux-дистрибутив.

Это возможно за счёт загрузки установочного окружения, подготовки накопителя и установки новой системы.

Для автоматизации удалённой установки существует инструмент **nixos-anywhere**, использующий SSH.

Он позволяет запускать установку NixOS на удалённой машине и интегрируется с инструментом декларативной разметки дисков `disko`.

Этот подход особенно интересен для серверной инфраструктуры.

Однако переустановка может привести к уничтожению существующих разделов и данных, поэтому перед экспериментом необходимо создать резервную копию и убедиться в правильности выбранного накопителя.

### 4.4. Сравнение способов установки

| Способ | Преимущества | Ограничения |
|---|---|---|
| NixOS с ISO | Полноценная система, высокая степень контроля | Требуется подготовка дисков и загрузчика |
| Nix поверх Linux | Не нужно менять основную ОС | Системная конфигурация остаётся под управлением другого дистрибутива |
| NixOS в виртуальной машине | Безопасное тестирование, возможность создавать снимки | Требует ресурсов хост-компьютера |
| Удалённая установка через SSH | Подходит для массового развёртывания | Нужны доступ по сети, права администратора и корректная конфигурация диска |

Для данного проекта наиболее рациональным вариантом является использование виртуальных машин.

Это позволит безопасно изучить установку, работу с конфигурациями, создание образов и сетевое развёртывание.

## 5. Преимущества и недостатки декларативного подхода

### 5.1. Преимущества

**1. Централизованное описание системы**

Большинство системных настроек можно собрать в одном наборе конфигурационных файлов.

Это упрощает анализ и повторное использование конфигурации.

**2. Контроль версий**

Файлы конфигурации являются обычным текстом, поэтому их можно хранить в Git.

Появляется возможность просматривать историю изменений, сравнивать версии и возвращаться к предыдущим описаниям.

**3. Повторяемость настройки**

Одна и та же конфигурация может использоваться для развёртывания нескольких машин.

При этом аппаратно-зависимые параметры и уникальные идентификаторы должны задаваться отдельно.

**4. Возможность отката**

Система поколений NixOS позволяет переключаться между сохранёнными системными конфигурациями.

**5. Изоляция зависимостей**

Параллельное хранение различных версий библиотек уменьшает количество конфликтов при установке программ.

**6. Удобство автоматизации**

Конфигурации могут использоваться для создания виртуальных машин, серверов и системных образов.

### 5.2. Недостатки

**1. Высокий порог входа**

Для эффективного использования NixOS необходимо изучить язык Nix, модульную систему и принципы работы Nixpkgs.

**2. Непривычная структура файловой системы**

Программы, предполагающие традиционное расположение библиотек и исполняемых файлов, могут потребовать дополнительной адаптации.

**3. Накопление старых поколений**

Сохранённые системные поколения и несколько версий программ могут занимать значительный объём накопителя.

Для освобождения места необходимо использовать средства сборки мусора Nix.

**4. Сложность некоторых сторонних приложений**

Программы, не учитывающие особенности NixOS, иногда требуют специальных упаковок или совместимых окружений.

**5. Ограниченная декларативность изменяемых данных**

Конфигурация не определяет автоматически содержимое пользовательских каталогов, баз данных, журналов и секретных ключей.

**6. Зависимость от качества конфигураций**

Неверное описание может привести к неработоспособности службы или системы. Декларативность облегчает восстановление известной конфигурации, но не заменяет тестирование.

### 5.3. Сравнение традиционного и декларативного администрирования

| Критерий | Традиционный подход | NixOS |
|---|---|---|
| Установка программ | Команды пакетного менеджера | Описания пакетов в конфигурации |
| Управление службами | Команды и конфигурационные файлы | Декларативные параметры модулей |
| История изменений | Требует отдельного контроля | Удобно интегрируется с Git |
| Откат системы | Зависит от используемых инструментов и снимков | Предусмотрены поколения конфигураций |
| Повторное развёртывание | Скрипты, образы или инструменты автоматизации | Конфигурация NixOS и инструменты развёртывания |
| Порог входа | Ниже для типичных задач Linux | Выше из-за необходимости освоить Nix |
| Работа с изменяемыми данными | Требует резервирования | Также требует резервирования |

Следует отметить, что традиционные дистрибутивы тоже поддерживают автоматизацию с помощью Ansible, Puppet, Salt и других инструментов.

Поэтому преимущество NixOS заключается не в исключительном наличии автоматизации, а в том, что декларативное управление встроено непосредственно в модель построения операционной системы.

## 6. Создание образа системы по описанию

### 6.1. Принцип создания образов

Системный образ представляет собой подготовленный набор данных, который можно использовать для запуска или установки операционной системы.

В NixOS конфигурация может служить основой для создания образа, содержащего необходимые пакеты, службы и системные настройки.

В зависимости от назначения возможны различные форматы:

| Формат | Назначение |
|---|---|
| ISO | Загрузочный носитель |
| QCOW2 | Виртуальные машины, прежде всего QEMU/KVM |
| RAW | Дисковые образы для различных платформ |
| Образы облачных платформ | Развёртывание в соответствующих облачных средах |

В современных версиях NixOS для создания системных образов предусмотрена команда:

```bash
nixos-rebuild build-image
```

Например, для сборки образа QCOW2 с использованием flake-конфигурации:

```bash
nixos-rebuild build-image \
  --image-variant qcow \
  --flake .#lab
```

Для создания ISO:

```bash
nixos-rebuild build-image \
  --image-variant iso \
  --flake .#lab
```

При этом конфигурация должна быть совместима с выбранным типом образа.

Начиная с NixOS 25.05, значительная часть возможностей ранее используемого проекта `nixos-generators` была включена непосредственно в Nixpkgs.

### 6.2. Пример декларативного описания веб-сервера

Рассмотрим конфигурационный модуль:

```nix
# modules/web.nix

{ pkgs, ... }:

{
  services.nginx.enable = true;

  services.nginx.virtualHosts."localhost" = {
    locations."/".return = "200 'NixOS Lab'";
  };

  services.openssh.enable = true;

  networking.firewall.allowedTCPPorts = [ 80 ];

  environment.systemPackages = with pkgs; [
    curl
    git
    htop
  ];
}
```

В данном описании задаются следующие требования:

- установлен и включён веб-сервер Nginx;
- запрос к корневому пути веб-сервера возвращает текст `NixOS Lab`;
- включён SSH-сервер;
- разрешён входящий TCP-трафик на порт 80;
- доступны утилиты Curl, Git и Htop.

Этот модуль может использоваться как общая часть конфигураций нескольких машин.

Для полноценной загрузки или установки потребуются также параметры оборудования, файловых систем, загрузчика, пользователей и доступа.

### 6.3. Практическое значение

Создание образа по описанию позволяет использовать одну конфигурацию для разных задач:

1. Формирования эталонного системного окружения.
2. Тестирования системы в виртуальной машине.
3. Подготовки образа для развёртывания.
4. Повторного создания системы после сбоя.
5. Проверки изменений перед установкой на рабочие серверы.

Таким образом, образ становится результатом управляемого процесса сборки, а не только копией однажды настроенного накопителя.

## 7. Клонирование систем по сети

### 7.1. Традиционное клонирование

Один из распространённых способов переноса системы между компьютерами — копирование содержимого накопителя.

Для этого применяются дисковые образы, инструменты резервного копирования и средства передачи данных.

Подобное клонирование может переносить не только программное обеспечение, но и пользовательские файлы, системные журналы, идентификаторы машины и секретные ключи.

Это удобно для создания точной копии диска, однако не всегда желательно при массовом развёртывании серверов.

Например, две машины не должны без необходимости использовать одинаковые SSH-ключи сервера.

### 7.2. Клонирование конфигурации в NixOS

В NixOS можно применять другой подход: вместо копирования всего диска повторно создать операционную систему из декларативного описания.

Общая схема процесса:

```text
Git-репозиторий
      |
      v
Конфигурация NixOS
      |
      v
Сборка системного окружения
      |
      +----------------------+
      |                      |
      v                      v
  Сервер A               Сервер B
      |                      |
      v                      v
 Nginx + SSH             Nginx + SSH
```

При таком подходе оба сервера получают одинаковую функциональную роль, но могут иметь разные аппаратные настройки и индивидуальные параметры.

Это позволяет развернуть несколько серверов из единого источника конфигурации.

### 7.3. Инструмент nixos-anywhere

Проект `nixos-anywhere` позволяет автоматизировать установку NixOS на удалённую машину через SSH.

В общем случае процесс включает:

1. Подключение к целевой системе.
2. Запуск установочного окружения NixOS, если это необходимо.
3. Подготовку дисков.
4. Установку системы по заданной конфигурации.
5. Завершение установки и подготовку системы к запуску.

Пример команды:

```bash
nix run github:nix-community/nixos-anywhere -- \
  --flake .#lab-b \
  --target-host root@192.0.2.20
```

Адрес `192.0.2.20` здесь условный и должен быть заменён на адрес экспериментальной машины.

Для полноценного применения команды необходима корректная конфигурация `lab-b`, включая схему разметки накопителя и средства последующего доступа.

**Важно:** удалённая переустановка может полностью удалить данные целевого компьютера. Для первого эксперимента следует использовать отдельную виртуальную машину и тестовый диск.

### 7.4. Инструмент disko

`disko` — инструмент декларативного управления разделами и файловыми системами.

Он позволяет описывать структуру накопителя в файле конфигурации Nix.

Например, можно определить:

- таблицу разделов GPT;
- загрузочный раздел EFI;
- основной раздел системы;
- файловые системы и точки монтирования.

Использование `disko` вместе с `nixos-anywhere` позволяет автоматизировать не только настройку программного обеспечения, но и подготовку диска для установки.

Это особенно полезно, когда требуется повторно создавать несколько однотипных серверов.

### 7.5. Ограничения сетевого клонирования

Клонирование NixOS по описанию не означает автоматического копирования всех данных.

Отдельного управления требуют:

- пользовательские файлы;
- базы данных;
- секреты и пароли;
- SSH-ключи;
- сетевые идентификаторы;
- сведения об оборудовании;
- разделы накопителей.

Таким образом, необходимо разделять **воспроизведение системной конфигурации** и **миграцию изменяемых данных**.

Это различие особенно важно при проектировании безопасного массового развёртывания.

## 8. Оригинальная исследовательская часть

### 8.1. Постановка исследовательского вопроса

Основной исследовательский вопрос сформулирован следующим образом:

**Какие компоненты NixOS действительно можно воспроизвести по исходной конфигурации, а какие требуют дополнительного управления или сохранения состояния?**

Для ответа предлагается экспериментально сравнить две виртуальные машины, развёрнутые на основе общего набора конфигурационных файлов.

### 8.2. Авторская модель трёх уровней воспроизводимости

В рамках проекта предлагается использовать аналитическую модель, разделяющую систему на три слоя.

**Слой 1. Описание**

Включает Nix-конфигурации, версии зависимостей, настройки сервисов и системные параметры.

Его воспроизводимость определяется полнотой описания и фиксацией используемых источников.

**Слой 2. Программные артефакты**

Включает построенные пакеты, библиотеки и системное окружение.

На этом уровне необходимо проверять идентичность результатов независимой сборки.

**Слой 3. Рабочее состояние**

Включает запущенные службы, сетевые настройки, базы данных, журналы и пользовательские файлы.

Здесь важна не только воспроизводимость конфигурации, но и корректное управление уникальными параметрами и изменяемой информацией.

Из модели следует, что полное клонирование машины можно рассматривать как более строгую задачу, чем воспроизведение её программной конфигурации.

### 8.3. План экспериментального стенда

Для проверки предлагается создать следующий стенд:

| Компонент | Назначение |
|---|---|
| Управляющий компьютер | Хранение конфигураций, сборка и запуск команд |
| Виртуальная машина `lab-a` | Первоначальная установка NixOS |
| Виртуальная машина `lab-b` | Повторное развёртывание по сети |
| Git-репозиторий | Хранение конфигураций и истории изменений |
| Nginx | Контрольная служба для проверки функциональной эквивалентности |

Предполагаемые ресурсы каждой виртуальной машины:

- 2 виртуальных процессорных ядра;
- 2 ГБ оперативной памяти;
- 20 ГБ дискового пространства;
- доступ к сети;
- поддержка SSH.

Эти параметры являются ориентировочными и могут корректироваться в зависимости от возможностей оборудования.

### 8.4. Методика проведения экспериментов

**Эксперимент № 1. Воспроизводимость конфигурации**

Цель: проверить, можно ли использовать одну базовую конфигурацию для создания двух NixOS-систем.

Порядок действий:

1. Создать общую конфигурацию для Nginx.
2. Зафиксировать зависимости через `flake.lock`.
3. Создать конфигурации машин `lab-a` и `lab-b`.
4. Развернуть обе системы.
5. Проверить наличие и работу Nginx на каждой машине.
6. Сравнить установленные службы и предусмотренные конфигурацией настройки.

Ожидаемый результат: обе машины выполняют одну и ту же функциональную задачу, но имеют разные системные идентификаторы.

**Эксперимент № 2. Проверка воспроизводимости сборки**

Цель: проверить воспроизводимость выбранного программного артефакта.

Для начала необходимо зафиксировать исходные данные сборки, версии зависимостей и архитектуру.

Для повторной проверки уже построенного пакета Nix предусматривает параметр:

```bash
nix build --rebuild
```

Он позволяет повторно собрать выбранный объект и сравнить результат с существующим.

Для более строгой проверки предполагается выполнить сборку на двух независимых окружениях, используя одинаковые входные данные, а затем сравнить полученные артефакты.

При этом следует отличать совпадение вычисленных путей Nix Store от фактической побитовой идентичности независимых результатов сборки.

**Эксперимент № 3. Откат конфигурации**

Цель: проверить возможность восстановления после ошибочного или нежелательного изменения системных настроек.

Порядок действий:

1. Создать работающее системное поколение.
2. Изменить настройки веб-сервера.
3. Активировать новую конфигурацию.
4. Зафиксировать изменение поведения службы.
5. Выполнить откат системной конфигурации.
6. Проверить восстановление прежнего поведения.

Проверяемые показатели:

- успешность восстановления;
- необходимость перезагрузки;
- время выполнения операции;
- сохранность пользовательских данных.

**Эксперимент № 4. Сетевое развёртывание**

Цель: определить, возможно ли автоматизировать повторную установку NixOS на другую машину.

Порядок действий:

1. Подготовить конфигурацию целевого сервера.
2. Настроить разметку диска через `disko`.
3. Запустить целевую виртуальную машину с подготовленным установочным окружением.
4. Обеспечить доступ по SSH.
5. Выполнить установку через `nixos-anywhere`.
6. Перезагрузить машину и проверить доступность Nginx.

Ожидаемый результат: система будет развёрнута на втором узле на основе ранее подготовленного описания без ручной повторной установки всех программ и служб.

### 8.5. Критерии оценки результатов

Предлагается оценивать результаты по следующим критериям:

| Критерий | Метод проверки |
|---|---|
| Успешность развёртывания | Система загружается и доступна по сети |
| Повторяемость конфигурации | Контрольные службы и настройки соответствуют описанию |
| Воспроизводимость сборки | Проверка побитовой идентичности выбранных артефактов |
| Эффективность отката | Восстановление прежней конфигурации |
| Скорость развёртывания | Измерение времени от запуска установки до готовности службы |
| Объём ручных действий | Подсчёт необходимых вмешательств администратора |
| Безопасность клонирования | Проверка уникальности ключей и идентификаторов машин |

Для каждого эксперимента необходимо сохранить команды, журнал выполнения и фактические наблюдения.

Это позволит сделать окончательные выводы на основании измерений, а не только теоретических предположений.

### 8.6. Научно-практическая ценность исследования

Оригинальность проекта заключается не в разработке нового пакетного менеджера, а в самостоятельной методике оценки воспроизводимости NixOS.

Предлагаемый подход объединяет три самостоятельные характеристики:

1. Воспроизводимость декларативного описания.
2. Воспроизводимость программных артефактов.
3. Воспроизводимость функционального поведения системы.

Такое разделение позволяет проверить распространённое утверждение о том, что NixOS предоставляет полностью воспроизводимое окружение, и определить реальные границы его применимости.

Результаты будут полезны для понимания того, в каких задачах декларативное управление эффективно, а где необходимы дополнительные инструменты управления состоянием и резервного копирования.

## 9. Предварительные результаты аналитического исследования

На основании изучения архитектуры NixOS и официальной документации можно сформулировать следующие наблюдения.

**Первое.** Декларативная конфигурация облегчает повторное создание системного окружения, поскольку настройки и зависимости описываются в текстовых файлах.

**Второе.** Использование `flake.lock` позволяет зафиксировать ревизии зависимостей, но не гарантирует автоматического устранения всех недетерминированных факторов сборки.

**Третье.** Механизм системных поколений позволяет выполнять откат конфигураций и снижает риски экспериментов с системными настройками. Однако он не заменяет резервного копирования изменяемых данных.

**Четвёртое.** Инструменты создания образов и удалённого развёртывания позволяют использовать NixOS для автоматизации подготовки нескольких машин.

**Пятое.** Для безопасного тиражирования серверов необходимо отделять общую конфигурацию от уникальных данных каждой машины.

Эти наблюдения являются результатами теоретического анализа. Экспериментальная проверка успешности и времени выполнения операций предусмотрена следующими этапами проекта.

## 10. Заключение

В ходе теоретического исследования была рассмотрена операционная система NixOS и её подход к декларативному управлению программным обеспечением и системной конфигурацией.

Установлено, что архитектура NixOS ориентирована на создание повторяемых окружений, сохранение системных поколений, контроль зависимостей и автоматизацию развёртывания.

Были изучены основные варианты установки NixOS: непосредственная установка на компьютер, использование Nix в существующем Linux-дистрибутиве и замена операционной системы через удалённый установочный процесс.

Также рассмотрены создание системных образов по описанию и возможность развёртывания нескольких машин с использованием общего набора конфигурационных файлов.

Сравнительный анализ показал, что декларативный подход обладает преимуществами при управлении конфигурациями, контроле версий и повторном развёртывании систем.

Вместе с тем он предъявляет дополнительные требования к квалификации администратора и не обеспечивает автоматического воспроизведения изменяемых данных.

Основной вывод исследования заключается в следующем:

**NixOS предоставляет мощные механизмы для воспроизводимого построения системной конфигурации, однако полная воспроизводимость программных сборок и эксплуатационного состояния требует дополнительного контроля и проверки.**

Предложенная методика экспериментов позволит установить, насколько эти механизмы эффективны на практике.

Таким образом, следующий этап проекта должен быть посвящён созданию рабочего стенда, установке NixOS, подготовке общей конфигурации и практической проверке повторного развёртывания систем.
